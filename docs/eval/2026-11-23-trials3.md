## What this re-run found

The first re-run on the current Driver caught **21/24** bugs. It missed `console-error` (clicking Add throws an uncaught error) in all 3 trials. Each time, the Judge saw the error and wrote that it "should be fixed", but still judged **pass**.

The Judge's instructions said errors are "problems even if the UI looked fine", but the verdict rule only failed a goal when a criterion was contradicted. So whether an uncaught error failed the goal was left to interpretation. The [previous eval](2026-11-22-trials3.md) read it one way (3/3 fail) and this one the other (3/3 pass). The Driver change didn't cause the miss; it exposed a rule that was ambiguous from the start.

**Fix** (`src/judge.ts`): every goal implicitly includes "the flow runs without errors". An uncaught error or failed request caused by the user's actions fails the goal. Errors unrelated to the flow are reported but don't fail it on their own.

The full eval was then re-run with the fixed Judge. The `no-blank` goal hit the Claude usage limit partway through, which made 5 runs inconclusive with the reason recorded. That goal was re-run on its own, and the tables below combine both runs: every case has 3 completed trials on the same code.

Compared with the 2026-11-22 run, the Driver now takes more actions per run (15.4 vs 9.8). It checks more, for example adding a second task, and the time per run is about the same.
